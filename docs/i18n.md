# Język i teksty w HomeBudget

Aplikacja, publiczne demo oraz strona obsługują angielski i polski. Główne README jest po angielsku, a `README.pl.md` zawiera polską wersję.

## Wybór języka

Przy pierwszym wejściu aplikacja korzysta z języka przeglądarki: polskiego dla `pl`, angielskiego w pozostałych przypadkach. Przełącznik EN/PL zapamiętuje wybór w `homebudget.language.v1`. Link `?lang=en` lub `?lang=pl` wskazuje język jawnie. Strona ma osobne, statyczne adresy dla PL (`/`) i EN (`/en/`), połączone odnośnikami `hreflang`.

Język jest wspólny dla strony i demo w tej samej przeglądarce. Przełączenie nie zmienia kwot, waluty ani identyfikatorów danych. Własne nazwy, notatki i opisy w instalacji użytkownika nie są automatycznie tłumaczone. Publiczne demo lokalizuje również swoje fikcyjne przykłady.

## Katalogi i formatowanie

- `budget-app/src/i18n/en.json`: angielskie komunikaty interfejsu, ze stabilnymi polskimi frazami jako kluczami.
- `pl.json`: poprawione polskie wersje, bez zmiany kluczy używanych przez kod.
- `errors.en.json`: komunikaty API przełożone na pomocne informacje dla użytkownika.
- `tr(source, params)`: reaktywne tłumaczenie w komponentach; dynamiczne wartości przekazuj jako parametry, nie sklejaj zdań.
- `intlLocale()`: wspólne formatowanie liczb, dat i kwot (`pl-PL` / `en-GB`). Waluta pozostaje PLN.
- `site/en.json`: angielska treść prezentacji. Build tworzy pełny angielski HTML z tego samego szablonu, bez tłumaczenia DOM w przeglądarce.

`npm run check:i18n` sprawdza wiadomości i parametry. Po zmianie katalogu uruchom testy aplikacji i Pages w obu językach. Nie tłumacz technicznych wartości `EXPENSE`, `REFUND`, kluczy API, identyfikatorów ani selektorów CSS.

Widoczne etykiety, np. `Kwota`, `Opis`, `Data`, `Sklep` i `Źródło przychodu`, są tłumaczone. Techniczne klucze pól w API (`amount`, `description`, `date`, `merchant`, `sourceId`, `name`) pozostają bez zmian. Tytuły edytora korzystają z gotowych wzorców `Dodaj: {0}` i `Edytuj: {0}` oraz zlokalizowanej nazwy elementu; nie buduj angielskich zdań przez doklejanie polskiego prefiksu.

## Jak piszemy

1. Pisz o tym, co użytkownik robi: „Dodaj wydatek”, „Wybierz sklep”, „Zapisz plan”.
2. Komunikat błędu mówi, co trzeba sprawdzić i jaki jest następny krok. Nie pokazuj surowego błędu serwera, parsera ani bazy.
3. Pusty widok proponuje sensowny początek zamiast samego „Brak danych”.
4. Te same czynności mają te same nazwy w całej aplikacji. Unikaj dosłownych tłumaczeń, które brzmią nienaturalnie.
5. Kwoty, zwroty, transfery i usuwanie danych wymagają spokojnego, precyzyjnego tonu. Bez żartów i obietnic, których aplikacja nie spełnia.
6. Tekst główny powinien być czytelny i mieć zwykłe odstępy między literami. Kolory i wyróżnienia opisują znaczenie, a nie dekorują każdą informację.

README i strona oddzielają język użytkownika od informacji dla programistów. Zależności, tokeny i szczegóły wdrożenia należą do dokumentacji technicznej, nie do zwykłych komunikatów aplikacji.
